Aufbau von OmegaSim

Stand dieses Artikels: OmegaSim 1.2.9 vom 26.10.2026 · Firmware des Autos: nicht bekannt (OmegaSim liest die Firmware-Version nicht aus)
Dieser Text wurde mithilfe von KI erstellt (Claude) und ist nicht in jedem Punkt von Menschen geprüft. Fehler bitte direkt verbessern oder auf der Diskussionsseite melden, siehe Mitmachen. Die öffentliche Fassung auf luuke42.github.io/omegasim kann älter sein als der hier beschriebene Stand.

Der Aufbau von OmegaSim beschreibt, woraus die App OmegaSim technisch besteht: in welchen Programmiersprachen sie geschrieben ist, wie aus rund 50 Quelldateien eine einzige auslieferbare HTML-Datei wird, wie dieselbe Datei als installierbare Web-App (PWA) und als Android-App läuft, wie sie sich selbst aktualisiert, wo sie Daten speichert, wie sie übersetzt und geprüft wird und wie der Motorklang entsteht. OmegaSim ist im Kern eine Web-Anwendung in JavaScript, die ohne Server und ohne Installation im Browser läuft und mit dem Carrera HYBRID über Bluetooth Low Energy spricht. Die Android-Fassung legt um dieselbe Datei eine dünne Hülle aus Java. Der Quellcode steht unter der MIT-Lizenz.

Grundlagen

Programmiersprache, Auszeichnungssprache, Stilsprache

  • HTML (Hypertext Markup Language) ist keine Programmiersprache, sondern eine Auszeichnungssprache: Sie beschreibt, welche Teile eine Seite hat (Überschrift, Knopf, Regler, Tabelle). In OmegaSim stehen dort alle Menüs, Optionen mit ihren ⓘ-Texten und die Patchnotes.
  • CSS (Cascading Style Sheets) beschreibt das Aussehen: Farben, Abstände, Schriften, Anordnung, Animationen.
  • JavaScript ist die Programmiersprache der Webbrowser. Sie macht die Seite lebendig: Sie liest den Controller, rechnet die Fahrphysik, baut die Bluetooth-Pakete und zeichnet die Karte.
  • Java ist eine Programmiersprache, in der klassisch Android-Apps geschrieben werden. OmegaSim nutzt sie nur für die dünne Android-Hülle.
  • Python ist eine Programmiersprache, die hier nur am Rechner des Entwicklers läuft: zum Bauen, zum Erzeugen von Klängen und Druckvorlagen und zum Auswerten von Bluetooth-Mitschnitten.
  • Apps Script ist das JavaScript von Google für Tabellen; damit läuft die Online-Bestenliste der Challenges in einer Google-Tabelle.
  • YAML ist ein Textformat für Einstellungen; die Bauaufträge von GitHub Actions sind darin geschrieben. JSON ist ein Textformat für Daten (Sicherungsdatei, Abstimmungen, Aktualisierungsliste).

Web-App, PWA und Service Worker

Eine Web-App ist ein Programm, das im Browser läuft und als Webseite ausgeliefert wird. Eine Progressive Web App (PWA) ist eine Web-App, die man zusätzlich wie eine App „installieren“ kann: mit eigenem Symbol, im Vollbild und ohne Adresszeile. Dafür braucht sie eine Manifest-Datei (Name, Symbole, Farben) und meist einen Service Worker. Das ist ein kleines Skript, das der Browser neben der Seite laufen lässt und das Anfragen an den Server abfangen und aus einem Zwischenspeicher (Cache) beantworten kann; so startet die App auch ohne Netz.

WebView und Capacitor

Eine WebView ist ein Browserfenster ohne Adresszeile, das eine Android-App in sich einbettet. Capacitor ist ein Rahmenwerk, das eine Web-App in eine solche WebView packt und ihr über Plugins Fähigkeiten des Telefons gibt, die eine Webseite nicht hat. Ein Plugin besteht aus nativem Code (hier Java oder Kotlin) und einer Schnittstelle, die JavaScript aufrufen kann. So kann OmegaSim in der App Bluetooth nutzen, obwohl die Android-WebView kein Web Bluetooth kennt.

Bauen, Version, Prüfsumme

  • Bauen (build) heißt, aus den Quelldateien das auslieferbare Ergebnis herzustellen. Bei OmegaSim ist das ein Zusammenfügen ohne Übersetzung: Die Dateien in src/ werden in Namensreihenfolge aneinandergehängt.
  • Eine Versionsnummer benennt einen Stand eindeutig. OmegaSim zählt sie automatisch aus der Git-Historie.
  • Eine Prüfsumme (hier SHA-256, geschrieben als 64 Hex-Ziffern) ist ein Fingerabdruck einer Datei: Ändert sich ein Byte, ändert sich die Prüfsumme. Die Selbstaktualisierung der App lädt nur Dateien, deren Prüfsumme sich geändert hat.

Gültigkeitsbereich und „temporale Todeszone“

Alle JavaScript-Dateien ab 10-ble-explorer.js bilden zusammen eine große Funktion, die sofort ausgeführt wird (eine IIFE, immediately invoked function expression). Sie teilen sich damit einen Gültigkeitsbereich: Eine Variable aus Datei 20 ist in Datei 90 sichtbar. Der Preis ist die temporale Todeszone: Wird eine mit let oder const angelegte Variable gelesen, bevor die Zeile mit ihrer Anlage durchlaufen wurde, bricht JavaScript die ganze Funktion ab, und die App bleibt leer. Laut tools/build.py hat das mindestens viermal zu Ladeabbrüchen geführt. Darum steht die Ladereihenfolge sichtbar im Dateinamen (20-, 40-, 90- …), und Variablen, die von mehreren Dateien gebraucht werden, stehen in der frühesten davon.

Bedienung

Für Nutzer ist der Aufbau unsichtbar. Für Mitwirkende sieht der Ablauf einer Änderung so aus (Einzelheiten in der Anleitung für KIs und unter Mitmachen):

  1. Quelltext in src/ ändern, nie die erzeugten Dateien index.html, sw.js, app-update.json.
  2. Neue sichtbare Texte in die Wörterbücher für Englisch und Spanisch in src/10-ble-explorer.js eintragen.
  3. Einen Selbsttest mit stAdd(…) in src/95-selftest.js ergänzen.
  4. python tools/build.py ausführen; der Bau meldet fehlende Verweise, verwaiste Wörterbucheinträge, Zugriffe auf nicht vorhandene Elemente und unausgeglichene Klammern.
  5. Die App öffnen, Entwickler → Selbsttest laufen lassen.
  6. Patchnotes ergänzen, python tools/bump_version.py ausführen, committen.
  7. Für eine neue Android-App einen Git-Tag apk-v… setzen; GitHub Actions baut die APK.

Eine Datei aus vielen: tools/build.py

Der Wert der App ist, dass index.html ohne Installation, ohne Server und ohne Bündelungswerkzeug läuft, auch direkt von der Festplatte. Die Quelle ist aber in Teile zerlegt. build.py hängt alle Dateien aus src/ mit der Endung .js oder .html in alphabetischer Reihenfolge byteweise aneinander, ohne Trenner.[1] Danach prüft es das Ergebnis:

  1. Verweise: Jedes lokale src= und href= muss auf eine vorhandene Datei zeigen, auch in auskommentierten Stellen.
  2. Wörterbuch: Eine verwaiste Zeile im englischen Wörterbuch wäre ein Syntaxfehler, der die ganze IIFE abbricht.
  3. Element-Kennungen: Zugriffe auf Elemente, die es im Dokument nicht gibt.
  4. Klammern: Zählung im gebauten JavaScript außerhalb von Zeichenketten, Kommentaren und regulären Ausdrücken. Eine Klammer zu viel ist ebenfalls ein Abbruch.
  5. Service Worker: sw.js wird aus der Vorlage tools/sw.js.in geschrieben; eine Marke in der Zeile const VERSION = … wird durch die Version aus index.html ersetzt.
  6. Aktualisierungsliste: app-update.json wird neu geschrieben (siehe unten).

Mit python tools/build.py --check baut das Werkzeug nichts, sondern vergleicht nur und nennt bei Abweichung Zeichen und Zeile der ersten Differenz.

Versionsnummer: tools/bump_version.py

Die Nummer wird vor jedem Commit aus der Git-Historie berechnet und in die Quelle (<span id="app-version"> in src/00-index.head.html) geschrieben; danach baut das Werkzeug index.html, sw.js und app-update.json neu.[2] 

woche  = (Montag dieser Woche − PROJEKT_START) / 7 Tage, abgerundet
push   = Commits seit Montag dieser Woche + 1 + PUSH_VERSATZ[Montag]
Version = 1.(woche − 10).push       wenn woche ≥ 10
Version = 0.woche.push               sonst
  • PROJEKT_START – fest der 03.08.2026 (Woche 0), weil die Historie mehrfach zu einem einzigen Commit zusammengefasst wurde
  • PUSH_VERSATZ – gibt einer Woche die Commits zurück, die beim Zusammenfassen verschwunden sind
  • + 1 – die Nummer gilt für den Commit, der gerade erst entsteht
  • VERSION1_WOCHE = 10 – ab der Woche vom 12.10.2026 beginnt die Zählung 1.x

Web-App und PWA

  • Manifest (manifest.webmanifest): Name „OmegaSim“, Start ./index.html, Darstellung standalone (ohne Browserleisten), Hintergrund- und Themenfarbe #000000, Symbole in 192 und 512 Pixeln, eines davon „maskable“ für runde Symbolformen.
  • Service Worker (sw.js): Beim Installieren legt er die „Hülle“ ab (index.html, Manifest, Favicon, Symbole) im Cache omegasim-<Version>; beim Aktivieren löscht er ältere OmegaSim-Caches. Die wichtigste Entscheidung: index.html wird Netz zuerst geholt, nicht Cache zuerst. Weil mehrmals am Tag neu veröffentlicht wird, würde ein Cache-zuerst-Arbeiter sonst eine alte Fassung zeigen, während die neue schon da ist. Nicht zwischengespeichert werden Anfragen, die nicht GET sind (etwa Meldungen an den Mehrspieler-Host), und Anfragen an fremde Ursprünge.[3]
  • Anmeldung (src/91-pwa.js): nur in einem sicheren Kontext, nicht über file:// und nicht in der Android-App, denn dort liefert die App ihre Dateien selbst und ein Service Worker wäre ein zweiter, veraltender Speicher. Der Knopf „Installieren“ erscheint nur, wenn der Browser die Installation anbietet (Ereignis beforeinstallprompt); auf iOS also nie, wo ohnehin kein Web Bluetooth zur Verfügung steht.

Die Android-Hülle

Die Android-App ist eine Capacitor-App mit der Kennung de.lroeseler.omegasim. Sie enthält dieselbe index.html unverändert (bestellt war eine APK, „die identisch zur HTML-App ist“); was nur in der App gebraucht wird, steht in der Seite hinter einer Abfrage von window.Capacitor und schläft im Browser.[4]

Bau der APK

Der Bauauftrag .github/workflows/android.yml startet, wenn ein Git-Tag der Form apk-v* hochgeladen wird (oder von Hand):[5]

  1. Rechner mit Java 21 und Node 22 vorbereiten.
  2. python3 tools/build.py und python3 tools/apk_www.py: Web-App bauen und genau die Dateien aus app-update.json nach android-app/www kopieren.
  3. Versionsname aus dem Tag (apk-v1.2.9 → 1.2.9), Versionscode als Haupt × 100000 + Neben × 1000 + Push.
  4. npm ci und npx cap sync android: Web-Dateien und Plugins ins Android-Projekt übernehmen.
  5. Signaturschlüssel aus den geheimen Einstellungen des Repositorys bereitstellen.
  6. ./gradlew assembleRelease: die APK bauen und signieren.
  7. Ein GitHub-Release mit der APK unter zwei Namen anlegen (mit Versionsnummer und als OmegaSim.apk).

Ein zweiter Bauauftrag (challenges.yml) holt stündlich zur Minute 17 die Bestenliste der Challenges und committet data/challenges.json nur, wenn sie sich geändert hat.

Selbstaktualisierung der App

Eine neue APK ist nur nötig, wenn sich die Android-Schicht ändert. Alles andere kommt als Web-Aktualisierung:[6]

  1. Beim Bau schreibt app_update.py die Datei app-update.json: Version, die nötige APK-Stufe (APK_STUFE = 2) und für jede Datei Pfad, SHA-256-Prüfsumme und Größe. Für 1.2.9 sind das 638 Dateien mit zusammen rund 23,6 MB. Textdateien werden mit Unix-Zeilenenden gehasht, weil die Arbeitskopie Windows-Zeilenenden hat, die veröffentlichte Fassung aber nicht.
  2. Beim Start fragt die App diese Liste von der veröffentlichten Seite ab. Ist die Version neuer, zeigt sie einen Hinweis.
  3. Verlangt die Liste eine höhere APK-Stufe als die installierte, meldet sie „neue APK nötig“ statt eines Web-Updates.
  4. Auf Tipp lädt das Plugin OmegaUpdate nur die Dateien mit geänderter Prüfsumme; alle anderen kopiert es aus der laufenden Fassung. Jede geladene Datei wird beim Schreiben nachgehasht.
  5. Die WebView wird auf den neuen Ordner umgestellt (Capacitor: serverBasePath).
  6. Die neue Fassung muss sich binnen 25 s als lauffähig melden (bestaetigen()). Tut sie das nicht, etwa wegen eines Syntaxfehlers, schaltet ein Wachhund auf die vorige Fassung zurück; wurde die App vorher beendet, geschieht das beim nächsten Start.
  7. Eine neu installierte APK setzt den Pfad zurück; dann gilt die mitgelieferte Fassung bis zur nächsten Aktualisierung.

Daten und Speicher

  • localStorage: Alles, was die App sich merkt (Einstellungen, Strecken, Autos, Rundenzeiten, Tastenbelegung, Sitzungen), liegt im localStorage des Browsers bzw. der WebView. Die Schlüssel beginnen mit chc., carrera-hybrid oder omegasim; die Sitzungshistorie steht unter chc.sessions.v1 (höchstens 200 Sitzungen). Seit 0.8.96 bittet die App mit navigator.storage.persist() darum, dass der Browser diese Daten nicht von selbst räumt.
  • Kein IndexedDB: Ein Umzug auf die größere Browser-Datenbank IndexedDB ist im Code ausdrücklich erwogen und nicht gemacht.[7]
  • Sicherungsdatei: Unter Optionen → Daten sichern schreibt die App alle Schlüssel mit den drei Präfixen in eine JSON-Datei omegasim-sicherung-JJJJ-MM-TT.json und liest sie wieder ein. Erfasst wird nach Präfixregel statt nach Liste, damit auch künftige Schlüssel mitkommen; ein Selbsttest prüft, dass jede bekannte Schlüsselkonstante unter die Regel fällt.
  • Android: Zusätzlich schreibt die App eine Sicherung nach Dokumente/OmegaSim. Weil eine Neuinstallation die Datei der alten Installation ab Android 11 nicht einfach lesen darf, öffnet sie sie über den Dateiwähler des Systems.

Übersetzungen

Die Oberfläche ist auf Deutsch geschrieben. Übersetzt wird zur Laufzeit über zwei Wörterbücher in src/10-ble-explorer.js: I18N_EN (mindestens 2 824 einzeilige Einträge) und I18N_ES (mindestens 1 102; gezählt wurden Zeilen der Form "…": "…").[8]

  • Schlüssel ist der deutsche Text selbst (Leerraum zusammengefasst), nicht eine Kennung wie options.rain.label. So musste am Markup nichts ausgezeichnet werden, und ein noch nicht übersetzter Satz bleibt deutsch stehen, statt zu verschwinden.
  • Spanisch fällt auf Englisch zurück, wenn ein Eintrag fehlt.
  • Ein Durchlauf ersetzt Textknoten und die Attribute title, aria-label und placeholder; ausgenommen sind SCRIPT, STYLE, CODE, KBD und alles mit data-i18n-skip. Ein MutationObserver übersetzt Inhalte, die später eingefügt werden.
  • Zusammengesetzte Texte („8 gemessene Runden, beste …“) laufen über die Funktion t(); Ansichten, die so zusammensetzen, melden sich an und werden beim Sprachwechsel vor der Übersetzung neu gezeichnet.
  • Nicht übersetzt werden Protokollzeilen und Bytewerte.

Selbsttest

Der Selbsttest misst die laufende App auf Knopfdruck (Entwickler → Selbsttest; mit ?st=Name in der Adresse nur passende Tests). Jeder Test wird mit stAdd(name, fn) angemeldet; fn gibt { ok, mass } zurück.[9] Drei Grundsätze stehen im Kopf der Datei:

  1. Jede Zeile nennt ihr Maß, nicht nur grün oder rot, damit man sieht, wie knapp es war.
  2. „nicht prüfbar“ ist ein eigenes Ergebnis, kein Fehler (etwa Tondateien, die über file:// nicht ladbar sind).
  3. Die Tests benutzen dieselben Funktionen wie die App, keine nachgebauten.

Beispiele: „Aufbau durchgelaufen“ verlangt mehr als 30 Regler und mehr als 400 Wörterbucheinträge; „Protokoll: CRC-8“ rechnet die Prüfsumme eines aufgezeichneten Pakets der Original-App nach. Zwischen den Tests gibt der Lauf dem Browser über einen MessageChannel Luft statt über setTimeout, weil Zeitgeber in verborgenen Fenstern gedrosselt werden. Am 26.10.2026 enthielt die Datei 522 Aufrufe von stAdd.

Klangerzeugung

Der Ton läuft über die Web Audio API des Browsers.[10]

  • Der AudioContext darf erst nach einer Nutzerhandlung starten (Regel der Browser gegen Autoplay); OmegaSim legt ihn beim ersten Klick oder Tastendruck an und verlangt die Latenzklasse „interactive“, weil eine Android-WebView sonst einen großen Puffer wählt und der Motor 100 ms und mehr hinter dem Gas herklingt.
  • Motorklang: Je Auto drei Schleifen (Leerlauf, mittel, hoch), deren Tonhöhe über playbackRate der Drehzahl folgt und zwischen denen überblendet wird. Die Schleifen liegen als Ogg-Dateien in audio/ (insgesamt 532 Ogg-Dateien, Herkunft in audio/CREDITS.md).
  • Erzeugt, nicht aufgenommen: Die Motorschleifen rechnet tools/engine_synth.py nach dem Ansatz des quelloffenen Projekts engine-sim (MIT-Lizenz): Ein Kolbenmotor klingt nach einer Folge von Verbrennungsstößen, geformt von der Resonanz des Auspuffs. Was Motoren unterscheidet, ist das Zündmuster: Ein gleichmäßig zündender Sechszylinder klingt glatt, ein V8 mit Cross-Plane-Kurbelwelle zündet je Zylinderbank ungleichmäßig und „blubbert“. Die Schleifenlänge ist eine ganze Zahl von 720-Grad-Arbeitsspielen, und alle Filter werden zyklisch angewendet, damit die Schleife ohne Knacken nahtlos wiederholt. Abtastrate 22 050 Hz.
  • Weitere Python-Werkzeuge erzeugen Umgebungsgeräusche, Boxen- und Hupenklänge (ambience.py, pit_sounds.py, horn_sounds.py) und Sprachclips für die Ansagen.
  • Die Motorwerkstatt (94-engine-workshop.js) rechnet dasselbe Modell im Browser, sodass Änderungen an den elf Stellgrößen sofort hörbar sind.

Die Versionsnummer 1.2.9

  1. Heute ist Montag, der 26.10.2026; Montag dieser Woche ist derselbe Tag.
  2. Vom 03.08.2026 bis 26.10.2026 sind es 84 Tage, 84 / 7 = 12, also woche = 12.
  3. 12 ≥ 10, also Hauptnummer 1 und Mittelzahl 12 − 10 = 2.
  4. Vor dem Commit von 1.2.9 standen seit Montag 0:00 acht Commits in der Historie, und für diese Woche ist kein Versatz eingetragen: push = 8 + 1 + 0 = 9 (aus der Nummer zurückgerechnet).
  5. Ergebnis: 1.2.9. Die APK dazu bekäme den Versionscode 1 × 100000 + 2 × 1000 + 9 = 102009.

Was eine Aktualisierung lädt

Angenommen, zwischen zwei Fassungen ändert sich nur index.html (rund 6,6 MB). Die App vergleicht die 638 Prüfsummen der neuen Liste mit denen der laufenden Fassung, findet eine Abweichung, lädt nur diese eine Datei und kopiert die übrigen 637 (rund 17 MB) lokal. Ohne Prüfsummen müssten alle 23,6 MB erneut geladen werden.

JavaScript: 91 001 Zeilen in src/*.js + 131 in tools/sw.js.in + 41 in Skriptblöcken = 91 173. Gesamtzahl 115 624. Anteil 91 173 / 115 624 = 0,7885, also 78,9 %.

Grenzen und bekannte Probleme

  • Die Zeilenzählung sagt wenig über Aufwand oder Schwierigkeit; ein Drittel des JavaScript ist Kommentar, ein weiteres Drittel Prüfcode.
  • Eine einzelne große IIFE ist empfindlich: Ein Syntaxfehler oder ein Lesezugriff in der temporalen Todeszone lässt die ganze App leer. Der Bau prüft deshalb Klammern und Wörterbuch, bevor die Datei ausgeliefert wird.
  • localStorage ist begrenzt und kann vom Browser geräumt werden (privater Modus, Aufräumen von Websitedaten, auf iPhones nach längerer Zeit ohne Besuch). Die Sicherungsdatei ist die Absicherung.
  • Web Bluetooth gibt es nur in Chrome und Edge; auf iPhone und iPad läuft die App nur als Info-Bildschirm.
  • Die Wörterbücher wachsen von Hand mit; Spanisch ist nicht vollständig und fällt dann auf Englisch zurück.
